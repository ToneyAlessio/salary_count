## 2026-11-09

### 多端形态：网页版 / 桌面版 / APP 版（设想，未立项）

来源：用户提出「以后有可能做成网页版、桌面版、APP 版」。当前**仅作记录**，不改动现有小程序正在进行的任何开发单元。

| 形态 | 用户怎么用 | 大致技术方向（仅科普，未选型） |
| --- | --- | --- |
| 微信小程序（现状） | 微信里打开，免安装 | 原生 WXML / WXSS / JS |
| 网页版 | 浏览器打开一个网址，不用安装 | HTML + CSS + JS，计薪公式可直接复用 |
| 桌面版 | Windows / macOS 上独立窗口，可离线 | 常见做法是把网页版用桌面壳（如 Electron / Tauri）包一层 |
| APP 版 | 手机桌面图标，能用系统通知等能力 | 原生开发，或跨端框架（如 Flutter / uni-app / React Native） |

**一条对现在就有用的结论**：同日定稿的计薪核心——日薪 ÷ 总秒数、用时间戳差值实时重算、跨天 +24h 并回溯上一班次——是**纯计算逻辑，不依赖微信的页面语法**。将来真做别的端，这部分可以原样搬过去，需要重写的只是界面和本地存储方式。这也是当初坚持「不用定时器累加、用时间戳重算」的额外好处。

**两条现在要忍住不做的事**：

1. 不为了「以后可能多端」提前抽公共层、加框架。小程序还没测试完，过早抽象会让当前代码变复杂，也更容易出 bug。
2. 不做技术选型、不建新仓库、不改目录结构。等小程序跑通并完成测试后，再按当时的实际需要重新评估。

**后续若要推进，需要先补的信息**（等用户确认后再填）：目标用户更常用哪个端、是否需要跨设备同步（这会引出账号和服务器）、是否要求离线可用。

## 2026-11-12

### 实时薪阶梯彩蛋（已确认，初版已做）

来源：用户希望实时薪资上涨时，用具体小物对应具体金额，带一点动态反馈。

| 实时薪达到（元） | 展示文案（示例） |
| --- | --- |
| ≥ 1 | ≈ 干脆面 |
| ≥ 7 | ≈ 珍珠奶茶 |
| ≥ 15 | ≈ 盒饭 |

**规则（v1）**：

- 仅 **上班中** 且未提前下班时，在实时金额下方显示当前所处 **最高档** 文案。
- 每升一档时做一次简短 **缩放动画**（`salary` 页 `milestoneText`）。
- 阈值表在 `miniprogram/utils/milestones.js`，以后要加档只改数组，不动计薪核心。
- 与提现、下班、存储 **无耦合**；提现后实时从 0 再涨，文案随金额重新升档。

**后续可扩展（未做）**：自定义档位、用户自填商品名、达到时震动或 toast、与小金库 / 摸鱼联动。
